状態: 方式非依存部分の設計草案。R0の合成試験は成立したが、実サイト・iOS実機の受入は未完。起動方式の確定と本番公開を意味しない。

## 1. 目的と責務

主表示は利用可能な公開Webアプリ、副表示は公開GitHubリポジトリの参照一覧とする。GitHub上の公開、Pagesの設定有効、URLの到達可能、実アプリの稼働、Hub内起動の互換性は互いに別の事実である。公開repoの存在からアプリ公開や埋込許可を推定しない。

- 収集・検証（R2/#5）: Publicのみの取得、ページネーション、公開候補・証拠の照合、安全なカタログ生成。
- カタログ: アプリ・公開repoの公開情報を一つの版付きsnapshotにする。UIを変更せずデータ更新できる。
- ランチャー（R3/#6）: アプリを検索・分類・選択する。GitHub参照は副次。表示設定・お気に入り等は端末所有。
- 起動（R4/#7）: アプリIDから確認済みURL・許可済みlaunch policyを解決し、起動・復帰・状態保持を管理。収集元のデータを埋込権限とみなさない。
- PWA（R5/#8）: Hub自体のインストール・更新・安全なキャッシュ。埋込先のオフライン動作を一律保証しない。

Site Kitの公開検索・site lifecycle等と意味が一致する部分は既存ownerの版付き契約を優先する。Repo MonitorのControl/開発状態投影をカタログとして流用しない。公開GitHub取得・ページングの共通機構はR2着手前に実装・テストまで照合する。Hub固有の台帳・起動状態はHub所有。既存repoへの一律導入は非目標。

## 2. データ

外部配布形状の正本は [catalog-snapshot.v1.schema.json](../schemas/catalog-snapshot.v1.schema.json)。schema検証に加え、相互参照・URL安全性・時刻・重複・出典の実証をアプリケーション契約で検証する。

| データ | 所有者・寿命 | 不変条件 |
|---|---|---|
| Repository | 収集器 / snapshot | GitHub numeric repository IDを文字列として保持。repo改名でIDを変えない。ownerはkinoko34077、公開と確認済みのものだけ。 |
| Application | 公開台帳 / snapshot | repoに0..Nアプリ。app keyは同一アプリのURL移動で変えない。repoに属する場合は repo:<repoId>:<key>、独立公開サイトは site:<key>。独立サイトは公開所有根拠を明示し、Private repoの代替掲載には使わない。 |
| CatalogSnapshot | 収集器→Hub / 更新単位 | schema version、生成時刻、最終有効時刻、完全な公開repo集合と確認済みアプリ。原子的に切り替える。 |
| LaunchPolicy | Hub管理者 / 版付き | app ID・確認済みcanonical URL・起動方式・許可能力・検証証拠の対応。外部収集結果と分離。未登録・URL変更・証拠失効時は内部起動不可。 |
| UserPreference | 端末 / 永続 | app ID単位のfavorite/order、最近使用、検索・表示・テーマ設定。名前・URLはcatalogから解決。消えたIDは起動させない。個人データを配信しない。 |
| RuntimeSession | Hub / セッション | active app ID、起動世代、復帰状態、エラー状態。実行中iframeや音声等は必要時だけ保持し、破棄時の復元は対応アプリの契約に限定。 |

Catalogのapp配列には所有・公開URLの確認を満たすアプリのみ入れる。ライブラリのデモ、開発プレビュー、資料ページは種別を明示し通常アプリの初期表示とは区別する。未公開・不明・到達不能・埋込不可は別状態。未公開・不明のURLを起動可能として出さない。repo一覧には公開が確認済みでもアプリがないrepoを表示できる。Hub自身はアプリ起動対象外。

## 3. 収集・更新・公開境界

1. 公開APIを最小権限で取得し、owner、repository ID、visibility=publicを再確認する。Privateデータの取得を設計前提にしない。ページング完了を観測し、エラーを空集合に変換しない。
2. Pages有効、明示homepage、公開デプロイ、管理者の公開サイト定義は候補発見の証拠。URL文字列を推測で確定しない。HTTPS・canonical URL・公開所有根拠・到達性を確認する。HTTP成功は機能やiframe互換性とは別。複数候補は同一アプリのaliasか別アプリかを識別する。曖昧な自動分類を確定扱いしない。
3. repo ID・app ID・canonical URLの重複、owner/visibility、参照整合、URL safety、時刻、allowlistフィールドを検証。表示テキストはtextとして扱い、HTMLを注入しない。資格情報付きURL・署名付き一時URL・非HTTPS・任意ローカルURL・秘密・Private由来情報を配信しない。候補URLのネットワーク検証は公開HTTPS宛のみに限定し、redirect先も再検証。任意外部URLのサーバー側取得を無条件で許可しない。
4. 完全取得・検証に成功したsnapshotだけを公開候補として作成。不完全取得・一時失敗では直前の有効snapshotを保持し、鮮度を表示する。既に公開取り消しを確認した項目を再掲載しない。新しい成功版は古いキャッシュを置換する。失効時刻を過ぎた版から新規起動しない。期限値はR2/R5で更新頻度・回復性・公開取り消しリスクを検証して決定。
5. オフライン端末の古い公開済み情報を完全回収できないことは明示的な境界。既に確認した非公開化は端末が受信した時点から表示・起動を止める。新規のPrivate情報を含めないことと過去公開情報の完全消去は同じ保証ではない。
6. 公開配信には最小限の明示フィールドのみ含める。生のAPI response・debug log・token・ローカルパスは配信しない。有料サービスは前提にしない。R2で自動更新と実行頻度を決定する。

## 4. 起動契約（R0依存部分は候補）

起動方式はデータ契約と独立に選べるようにする。Hubがユーザー操作のapp IDを解決する。URLパラメータで任意URLを受けない。既定は内部起動未承認。内部起動の可否は公開URLに紐付けた管理者所有のLaunchPolicyと実証証拠で決定する。非対応・未検証の場合には理由を表示して、必要時のみ明示的外部起動を選べる。自動外部遷移しない。

候補は sandboxed iframe（opaque / 別origin / 信頼済み同一originの区別）、同一origin内のscope遷移、契約を持つ直接統合。R0で検証し最終決定する。同一originは相互DOM・storage等へのアクセス可能性があり、隔離とみなさない。allow-scripts + allow-same-origin の組合せを同一originの安全境界にしない。権限は個別に必要最小限。CSP/X-Frame-Optionsの迂回、未信頼の埋込、認証情報の共有を行わない。postMessageを導入する場合は送信元origin・Window・型・状態を検証する専用契約が必要で、初期実装の必須条件ではない。

通常利用ではHubの表示領域を最大化し、復帰・切替の操作点だけを維持する。active appが消えた、URLが変わった、許可が失効したときは自動で新URLを起動しない。状態を保持する場合は音声・メモリ・再生停止などの副作用とアプリの正式な復元契約を確認する。
